# 茶叶图像数据标准化平台（PWA）

面向茶叶科研/质检的**图像数据采集与标准化**工具。桌面端负责复杂的批量管理，手机端负责现场采集；
两端共用同一套业务逻辑与路由，仅布局壳不同。核心流程：**标签登记 → 四槽位图像采集编辑
（外形 / 茶汤第1冲 / 茶汤第2冲 / 叶底）→ 确认登记 → 数据记录 → 批量重命名 →
一键打包下载（ZIP）**。

## 技术栈

- React 18 + Vite 5 + TypeScript
- Tailwind CSS v3 + 自建轻量原子组件（等价 shadcn/ui，避免 CLI 初始化耦合）
- Zustand（根状态）/ Dexie（IndexedDB 持久化）
- React Router v6（桌面/手机共用路由）
- react-image-crop（圆形裁剪）、JSZip（打包）、exifr（EXIF 读取）、vite-plugin-pwa（PWA）

## 架构与模块边界（关键约定）

工程严格分层，**业务模块之间零耦合**，跨模块只通过基础设施层通信。

```
src/
├─ infrastructure/         # 模块唯一通信通道，业务模块只依赖此层
│  ├─ types.ts             # 领域数据模型（全模块共用契约）+ 槽位定义表 SLOTS（单一事实来源）
│  ├─ repository/          # 数据访问抽象接口（Sample/Asset/Option）
│  ├─ capabilities/        # 能力注册表（相机/导出/EXIF/色彩烘焙/预设查找）
│  ├─ event-bus/           # 发布订阅（mitt），如 asset:updated / sample:created
│  ├─ store/               # 根 Zustand（在线状态/主题），各业务模块自有 store
│  ├─ utils/               # useMediaQuery / uid / downloadBlob / useObjectURL …
│  └─ router/              # 路由表 + Desktop/Mobile 双 Shell 切换
└─ modules/                # 11 个业务模块，彼此不互相 import
   label · quality · image-editor · record · export
   camera · device · color-profile · theme · storage · pwa
```

- **依赖倒置（repository）**：`storage` 在启动期把 Dexie 实现注册进 `infrastructure/repository`，
  其他模块只消费接口，不直接引用 `storage`。
- **能力注册表（capabilities）**：`camera`/`export`/`device`/`color-profile` 在启动期各自注册能力
  （相机组件、ZIP 打包、EXIF 提取、色彩烘焙、预设查找），调用方经 `getXxx()` 取用，互不 import。
- **事件解耦（event-bus）**：`image-editor` 完成编辑 → 发 `asset:updated` → `quality` 订阅刷新槽位，
  无需直接引用对方。
- **双端同构**：单 bundle，`router` 按 `useMediaQuery('(min-width: 768px)')` 切换
  `DesktopShell`（侧边栏/表格/批量）与 `MobileShell`（底部导航/大按钮/相机优先）。

修改任意单个模块（如 `image-editor`）不影响其他模块运行。

## 采集槽位与拍摄规范

**槽位定义表**（`infrastructure/types.ts` 的 `SLOTS`）是采集项的唯一事实来源：UI 布局、登记就绪判定、
标准文件名、导出列名均由它驱动。**增删槽位只需改这一张表**。

| 槽位键 | 展示名 | 归属维度 | 必填 | 拍摄说明 |
|---|---|---|---|---|
| `shape` | 外形 | 外形 | 是 | 干茶匀整度 |
| `soup` | 茶汤第1冲 | 茶汤 | 是 | 第 1 冲泡汤色 |
| `soup2` | 茶汤第2冲 | 茶汤 | **否（选填）** | 第 2 冲泡汤色 |
| `leaf` | 叶底 | 叶底 | 是 | 叶底匀亮度 |

- **「维度」用于分组与列语义，「槽位」用于图像身份与存储键**。茶汤含 2 个槽位，
  两者维度同为 `soup`；存储键必须用槽位（若用维度，两张茶汤会互相覆盖且不报错）。
- **登记就绪判定**：标签完整 + 全部**必填槽位**完成编辑确认。茶汤第2冲为选填，未采集不阻塞确认登记。

### 两冲泡汤色的方法学约束（拍摄可比性）

「茶汤第1冲 / 第2冲」表达的是**冲泡次序**，两张图在时间上是先后关系而非同一时刻的两种拍法。
若拍摄条件不一致，色差将无法归因于茶样本身。实际采集请遵守：

| 约束 | 目的 |
|---|---|
| 两冲出汤后**各自在固定同一时长内完成拍摄**（建议 30 s 内） | 避免茶汤氧化加深的速率差混入"放置时长"这一混杂因素 |
| **同器、同量、同光源、同机位俯拍**（同一审评碗/品茗杯、等量茶汤、同一光源与相机高度） | 使两冲唯一变量为冲泡次序本身 |
| 同一样品的两冲应由**同一次审评流程**连续完成，中途不更换拍摄环境 | 保证批次内可比 |

> 若研究需要第 3 冲及以后，只需在 `SLOTS` 表内追加一行（如 `soup3` + 展示名）并同步
> `SlotKey` 类型，UI、判定、文件名与导出列名会自动跟随。

## 核心流程

登录/打开 → `/label` 登记标签（类别/名称/年份/等级，类别与等级可自定义新增）→
`/quality/:sampleId` 采集四槽位（外形 / 茶汤第1冲 / 茶汤第2冲 / 叶底；相机或上传，
进入 `/edit/:assetId` 圆形裁剪）→ 校验（标签完整 + **必填槽位**均确认）后「确认登记」→
`/record` 查看、重命名、冲突检测、批量操作 → 一键打包 ZIP 下载。

## 色彩矫正（已接入编辑器）

平台通过「设备型号 → 色彩矫正参数」映射表实现跨机型色彩标准化：

- 映射表在「设置 → 色彩矫正映射表」维护（localStorage 持久化，**非硬编码机型**），可增删预设。
- 参数以**数字输入框**录入（替代早先的滑杆），每项右侧常驻显示上下限；输入越界时边框转警示色，
  **失焦时自动钳制到上下限**并按定义表小数位规范化。
- 进入图像编辑页时，按当前样品的 `deviceInfo.model` 解析预设（命中具体机型回退通配 `*`）。
- 编辑器提供「应用色彩矫正」开关：开启后，**实时预览与导出文件均烘焙该预设**；
  原图始终保留，`editedFile` 为矫正后结果，`asset.colorProfile` 记录实际应用的参数。
- 确认登记时，`sample.colorProfile` 同步写入，供记录/导出元数据展示。

### 参数表（单一事实来源：`infrastructure/types.ts` 的 `PARAM_SPECS`）

| 参数 | 键 | 下限 | 上限 | 步长 | 中性值 | 小数位 | 映射到 CSS filter |
|---|---|---|---|---|---|---|---|
| 色温 | `temperature` | -500 | 500 | 10 | 0 | 0 | 经 `brightness` 近似 |
| 色调 | `tint` | -100 | 100 | 1 | 0 | 0 | `hue-rotate(tint × 0.4deg)` |
| 曝光 | `exposure` | -2.00 | 2.00 | 0.05 | 0 | 2 | `brightness(2^EV)` |
| 饱和度 | `saturation` | 0.5 | 1.5 | 0.01 | 1 | 2 | `saturate(v)` |
| 对比度 | `contrast` | 0.5 | 1.5 | 0.01 | 1 | 2 | `contrast(v)` |

亮度通道的合并公式（`color-profile/service.ts` 的 `filterString`，**预览与烘焙的唯一出口**）：

```
brightness = clamp( (100 + temperature / 10) / 100 × 2^exposure, 0.01, 8 )
```

> **⚠ 色温与曝光共用亮度通道，二者非正交，请按语义区分使用。**
> 色温当前以 ±50% 亮度偏移**近似**实现（并非真实色温/白平衡），曝光按 EV 换算为线性亮度增益，
> 因此 `+500K` 与 `+0.5EV` 在视觉上都表现为"整体变亮"。
> 真正的通道级色温（R×kr / B×kb 增益矩阵）需逐像素处理（1024² ≈ 100 万像素，约 50–120 ms/张），
> 属后续可选项，当前未实现。**录入约定：色温调冷暖，曝光调明暗。**

> **曝光取值依据**：±2 EV 覆盖手机摄影常见测光偏差；步长 0.05 EV ⇒ 亮度步进 `2^0.05 ≈ 1.0353`，
> 即约 3.5% 亮度增量，在 8bit 输出下约对应 4–5 个色阶，适合精细校准。

> **预览区**：底色固定为中性灰 `#808080`（色彩与明度判断不受主题切换干扰，是校色场景的标准做法）；
> 「按住看原图」可按压即时对比矫正前后。桌面端预览高度 `clamp(320px, 46vh, 560px)`，
> 参数列为定宽 280–320px，其余宽度全部让给预览。

> **映射表存储与迁移**：v2 起存储为 `{ version: 2, list: [...] }` 信封（v1 为裸数组，仍可读取）。
> 读取时逐字段回退到 `PARAM_SPECS` 的中性值，并立即回写新格式。
> **这一步不可省略**：缺失字段会让 filter 产出 `brightness(NaN)`，而按 CSS filter 规范，
> 列表中**任一函数无效会导致整条 filter 值被判定失效并静默丢弃** ——
> 届时色温/色调/饱和度/对比度四项也会一并失灵，且控制台无任何报错。
> 注意：新信封对**本版之前的旧构建不可读**（旧代码会把信封当数组用）。如需回滚到旧版构建，
> 请先在浏览器控制台执行 `localStorage.removeItem('tea-color-profiles')`，再刷新页面即可回到默认预设。

> **通配项（`deviceModel === '*'`）是系统保证项，不可删除**。
> 它是所有「未匹配到具体机型」样品的唯一兜底出口。删掉它的后果不可自洽：未匹配机型会在编辑页
> 落入"无预设"状态 —— 连「应用色彩矫正」开关都不渲染，用户在该页无法自救。
> 因此本版做了三处约束：
> 1. 设置页**禁止删除**通配项（删除按钮置灰，`remove` 内亦有二次拦截）；
> 2. `loadProfiles()` 读取时若发现通配项缺失，**自动补齐并回写** —— 只追加到末尾，
>    不删除也不重排，用户既有条目原样保留；
> 3. 设置页常驻显示「映射表共 N 条 / 通配项状态」，供自检。
>
> **排查指引**：编辑页若出现「当前样品未匹配到色彩预设」，先到「设置 → 色彩映射表」看通配项状态。
> 显示"缺失"时刷新一次页面即会由读取路径自动补齐；若为"已配置"仍不命中，则说明色彩模块未注册
> （构建异常），此时编辑页会给出前往设置页的入口。

> **预设匹配语义**（`color-profile/service.ts` 的 `matchProfile()` 是唯一实现，设置页与编辑页共用）：
> 匹配序为 **精确机型 → 通配项 → 未命中**，结果分三态：
>
> | 结果 | 含义 | 编辑页表现 |
> |---|---|---|
> | `exact` | 样品机型与某条预设的「匹配设备型号」逐字相同 | 「匹配机型：xxx」 |
> | `wildcard` | 未命中具体机型，回退通配项 | 琥珀色提示「未命中具体预设，已回退通配项」+ 前往设置入口 |
> | `none` | 连通配项都没有（列表被外部写坏 / 色彩模块未注册） | 「当前样品未匹配到色彩预设」 |
>
> 机型比较前**两侧均 `trim`**：机型是自由输入字段，首尾空白会造成"看起来一样却匹配不上"。
>
> **⚠ 两个「机型」不是一回事，排查前先分清**：
> - 设置页「设备信息」读写的是**全局** root store（`useRootStore.deviceInfo`，localStorage）；
> - 编辑页匹配用的是**样品创建时的快照** `sample.deviceInfo.model`（IndexedDB），
>   由 `label/service.createDraft(deviceInfo)` 在登记时写入。
>
> 所以在设置页改了型号，**已有样品不会跟随变化**。判断"预设为何没生效"必须看**编辑页显示的样品机型**，
> 而不是设置页的全局型号 —— 这是本项目最容易踩的一处认知陷阱。
>
> **设置页「命中自检」**：以全局设备型号为参照，按**编辑中**（未保存也生效）的列表实时计算
> 「将使用哪条预设」，并逐条标出 `✓ 精确命中` / `✗ 未命中` / `通配兜底`。
> 旁边的「填入当前设备型号」按钮可把全局型号原样写进当前预设的匹配字段，用于消除手输错字与
> 全角/半角括号差异 —— 这两类差异在下拉框里根本看不出来，却是"预设不生效"最常见的成因。
>
> **下拉框文案**为 `设备型号 → 预设名称`（如 `2026 → 专业相机`、`* → 原图（默认）`）。
> 旧版文案 `预设名称（设备型号）` 会渲染成「专业相机（2026）」这种与「机型名（年份）」撞车的写法，
> 把填错的型号伪装成正确配置，已弃用。

> 说明：当前色彩矫正基于 CSS `filter`（对比度/饱和度/亮度/色相旋转）近似实现，非 ICC 级色彩管理，
> 适用于科研样本的快速可比标准化，不替代专业校色流程。

## 裁剪模式（正方形 / 圆形）

编辑页「裁剪模式」提供两档可选，默认**圆形**（与历史产出形态一致，避免静默改变既有行为）。
形状定义在 `infrastructure/types.ts` 的 `CROP_SHAPES` 表 —— 新增形状只需追加一行，
分段控件、蒙版绘制、预览与缩略图轮廓、导出列名全部自动跟随。

### 形状与几何是两层，互不干涉

| 层 | 内容 | 切换形状时 |
|---|---|---|
| 呈现层（形状） | 输出蒙版：圆形裁切 / 整幅方形 | **改变** |
| 编辑层（几何） | 裁剪框位置与大小、缩放、旋转、输出尺寸 / 格式 / 底色、色彩矫正 | **完全保留** |

**为什么能做到零损失**：裁剪框是 `aspect=1` 的百分比矩形，两种形状共用同一个选区，
区别只在于「选区内的哪些像素被保留」。因此切换形状不需要任何坐标换算，也无需清空用户的编辑。

### 交互表现

- 切换控件为两态分段按钮，选中态以主色填充，下方给出一句该形状的语义说明。
- 切换即时反映在三处：① **裁剪框叠加层**（圆形叠加圆形遮罩、四角压暗；方形为直角手柄）；
  ② **实时预览画布轮廓**（见 `cropShapeRadius()`：圆形 `50%`，方形 `var(--radius)`）；
  ③ 确认后的**产物像素**。
- 编辑页会恢复该资产**已保存**的形状。否则重新编辑一张方形产出时会默认回到圆形，
  用户只点一次「确认」就把产物静默改回圆形 —— 这类不可见的状态翻转必须避免。

### 输出与导出

| 项 | 正方形 | 圆形 |
|---|---|---|
| 预览 / 导出像素 | 整幅 1:1，无透明区 | 方形画布 + 四角 `alpha=0` |
| 缩略图与槽位卡轮廓 | 圆角矩形 | 正圆 |
| `metadata.csv` | 新增 `<槽位>裁剪形状` 列，取值「正方形」 | 同左，取值「圆形」 |
| `metadata.json` | 新增 `cropShapes` 对象，取机器键 `square` | 同左，取 `circle` |

> 形状列**成块**排在各槽位「文件」列之后，既有列（设备型号 / 色彩矫正 / 登记时间）相对顺序不变。
> 圆形产出的四角为 `alpha=0`，作全域色值或明度统计前请先按该列排除。

### 已知边界：正方形 + 旋转

正方形模式下若同时旋转，旋转后的方片盖不住画布四角，会露出底色（透明或白）。
圆形不受影响 —— 旋转正方形的**内切圆**恒在其内部。

界面按**充要条件**判断并给出可执行数字，而非笼统提示（见 `types.ts` 的 `cropCoverScale()`）：

```
覆盖条件：scale ≥ |cosθ| + |sinθ|        θ = 0° → 1.00；θ = 45° → √2 ≈ 1.41
```

缩放已达标时不再提示，避免把提示变成噪音。

### 向后兼容

`CropMeta.shape` 为**可选**字段，读取统一经 `cropShapeOf()` 兜底为 `'circle'` ——
历史资产全部是圆形产出，故兜底语义正确，**无需升级 Dexie 版本**（与 `slotOf()` 同一范式）。

## 主题

内置 3 套主题（极简 iOS 风 / 茶韵国风 / Material You 风），由 CSS Variables（Theme Token）
驱动，「设置 → 主题」切换。主题**只改视觉，不改变任何业务逻辑**。默认：极简 iOS 风。
主题选择经根 Store（zustand persist）持久化；已下线的主题 id 会被白名单校验自动纠正回默认值。

## PWA 与部署要求

- 构建产物 `dist/` 含 `sw.js`（离线缓存 app shell）与 `manifest.webmanifest`（可安装到主屏）。
- **硬性前提**：相机（`getUserMedia`/`ImageCapture`）、`beforeinstallprompt` 安装提示、EXIF 读取
  均依赖**安全上下文（HTTPS 或 localhost）**。本地 `npm run dev` 可用；真机必须经 HTTPS 部署，
  否则相机专业模式与安装提示会被浏览器拦截。
- 部署：将 `dist/` 托管到任意支持 HTTPS 的静态服务器/CDN 即可，Service Worker 自动注册。

## 已知边界与后续

- 色彩矫正为 `filter` 近似，非 ICC 级。其中**色温以亮度偏移近似、并无独立的色相通道**，
  与曝光共用 `brightness`；如需真正正交的通道级色温，升级路径为在 `bakeProfile` 内做
  R×kr / B×kb 增益矩阵（逐像素，1024² 约 50–120 ms/张）。
- 「网络恢复后同步」当前仅留事件接口（`online:changed`），未接远端服务器。
- 单样品建议 ≤ 4×8MB（1024² PNG/WebP），超出会提示，防止 IndexedDB 膨胀。
- 相机专业控制（对焦/曝光/变焦/白平衡）依赖浏览器能力探测，不支持时自动降级为普通拍照 + 上传。
- **数据库版本**：茶汤拆为两个槽位时数据库由 v1 升至 v2（Dexie 内部版本号 10 → 20）。
  升级为纯增量迁移：为历史资产补 `slot` 字段、为历史样品补 `soup2` 空位，不搬移既有键、不动 Blob，
  幂等可重入。读取路径对缺失 `slot` 的历史数据有 `slotOf()` 兜底。
  历史样品的首个茶汤文件名会由 `…_茶汤_001.png` 变为 `…_茶汤第1冲_001.png`；
  如需刷新，在记录页对老样品执行一次「批量自动编号」即可。
- **对外契约变化**：导出 `metadata.csv` 的列名由「茶汤文件」变为
  「茶汤第1冲文件 / 茶汤第2冲文件」；`metadata.json` 的 `files` 键为 `shape / soup / soup2 / leaf`。
  若有下游脚本按列名读取，需同步调整。
  另：`metadata.json` 的 `colorProfile` 对象自本轮起新增 `exposure` 字段；
  `metadata.csv` 的「色彩矫正」列仍只写预设名，**列名与列数均未变化**。
  若下游对 `colorProfile` 做严格 schema 校验或固定键名解析，需同步放行该字段。
